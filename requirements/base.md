# ゲームの出欠をとるアプリケーション 要求仕様

金曜の定期開催と任意日の「桃鉄1年勝負」の出欠を、Discord Bot を用いて自動化するアプリケーションの要求仕様を定める。

> 原文の要求（概要）
> 毎週開催している深夜の桃鉄1年勝負の出欠をとりたい。Discord 上で固定4名の出欠をとり、全員出席なら開催、誰か欠席 / 22時前に未返答があれば中止し、翌日順延の可否を確認する。
>
> ※ 原文の「22時前」は発案時の粗い表現であり、確定した締切は §3.1 の「金 21:30 JST」を正とする。

本書は **業務要求（What / Why）の正典** である。実装手段・技術選定・運用手順・コーディング規約は本書の対象外とする。

---

## 1. 概要

- **対象イベント**: 毎週金曜日深夜を基本とし、手動で任意日にも募集する桃鉄1年勝負
- **対象メンバー（固定4名）**: 設定した Discord User ID で識別する。本書の文面例では、表示名を「メンバーA」〜「メンバーD」とする。
- **基準タイムゾーン**: JST (Asia/Tokyo)。本書のすべての時刻表記は特記無き限り JST。
- **運用チャンネル**: 専用チャンネル（例: `#桃鉄出欠`）1 箇所。Bot のすべての投稿・インタラクションはこのチャンネルに限定する。
- **固定4名以外の操作**: 無視する（コマンド実行・ボタン押下ともに）。

---

## 2. 全体フロー

```
[金曜 08:00] 自動で出欠確認メッセージを送信（/ask でも手動起動可）
        │
        │ 4名が5ボタン [22:00][22:30][23:00][23:30][欠席] のいずれかを押す
        │ ※ 締切 21:30 までは回答変更可能
        │
        ├─ 誰かが [欠席] を押下 ─────────→ 即時中止 ─→ 順延確認フローへ
        │
        ├─ 締切 21:30 時点で未回答者あり ──→ 中止確定 ─→ 順延確認フローへ
        │
        └─ 締切 21:30 時点で 4名全員が時刻選択 ─→ 開催確定フローへ
```

---

## 3. 出欠確認（募集）フェーズ

### 3.1 送信タイミングと募集の単位
- **自動送信**: 毎週金曜 **08:00 JST**。週次自動募集は1週に1件。停止済み・生成済みの場合は作成しない。
- **手動送信**: 固定4名が `/ask` を実行した当日を開催候補日にする。曜日を問わず、**当日21:30より前**だけ受け付ける。guild / channel / 固定4名の検証は常に行う。
- **日付の一意性**: JSTの同じ開催候補日には最大1件。中止・完了後もその日を再募集しない。同一ISO週でも別日なら募集できる。
- **進行中の一意性**: `ASKING` / `POSTPONE_VOTING` / `DECIDED` / `CANCELLED` はBot全体で最大1件。前週分を含め、進行中の募集があれば新しい手動・自動募集を拒否する。古い募集を強制終了させたり、手動募集を待機列に入れたりしない。
- 自動送信と手動送信の競合でも日付・進行中の一意性を守る。同じ操作の再送は既存結果へ収束し、別日・別週の新しい募集にしない。
- 金曜08:00前の手動募集は可能。その日を使用するため、08:00以降の自動募集は作られず、手動募集には順延を付けない。
- **取りこぼした自動募集の復旧**: 金曜08:00以上21:30未満に限り、起動・再接続・既存schedulerの再計算で再判定する。古い進行中募集の期限処理・必要なリマインド配送が実際に完了した後に作成できる。21:30以降や翌日の補完はしない。専用の待機列・追加pollingは持たない。
- 週次自動募集から順延が成立したときだけ、その直後に翌日（土曜）回を作成・送信する（§6）。

### 3.2 募集メッセージ構成
- **メンション**: 固定4名全員
- **本文**（例）:
  ```
  🎲 桃鉄1年勝負、出欠確認です

  開催候補日: 2026-04-24(金) 22:00 以降
  回答締切:   21:30
  ボタン:     参加できる一番早い時間を選んでください
  補足:       23:00 を選ぶと 23:00/23:30 に参加できるものとして集計します
  予定が合わない場合は「今回は欠席」を選んでください（今回はお流れになります）

  回答状況
  - メンバーA : 未回答
  - メンバーB : 未回答
  - メンバーC : 未回答
  - メンバーD : 未回答
  ```
- **ボタン（横1列・5個）**: `22:00` / `22:30` / `23:00` / `23:30` / `今回は欠席`

### 3.3 回答挙動
- 4名それぞれが5ボタンのいずれか1つを押して回答する。
- 回答は **募集メッセージ本文を編集して全員に可視化**する（各メンバーの選択 or 「未回答」）。
- **回答の変更**: 締切（21:30）までは自由に押し直し可能。最後に押したボタンを有効とする。
- **中止確定後**（欠席押下 or 締切未回答）は全ボタンを無効化し、以降の変更は不可。

## 4. 判定ロジック

### 4.1 中止確定（以下のいずれかで中止確定）
| 条件 | 発動タイミング |
|---|---|
| 誰か1人が `欠席` を押下 | 押された瞬間に即時 |
| 締切（候補日当日21:30）時点で未回答者が1人以上残存 | 締切到達時 |

中止確定後、金曜の週次自動募集だけが §6 の順延確認へ進む。手動募集・順延先の募集は終了する。

### 4.2 開催確定
- **締切（21:30）時点で 4名全員が時刻ボタンを選択している**ことが条件。
- **集計ルール（「それ以降参加可能」解釈）**:
  - 各ボタンの意味: 「その時刻以降に参加可能」
  - 22:00 選択者は 22:00 / 22:30 / 23:00 / 23:30 すべてで参加可能
  - 23:00 選択者は 23:00 / 23:30 のみ参加可能
  - **開始時刻 = 4名の選択時刻のうち最遅のもの**（= 全員が参加可能な最早時刻）
- タイブレーク不要（開始時刻は常に一意に確定する）。
- 締切前に全員が時刻選択を終えていても、開催確定は **締切時点** で行う（それまでは暫定表示）。

### 4.3 暫定状態の表示
全員が時刻選択済みだが締切未到達の間は、募集メッセージの末尾に開始見込みを表示する：
```
いまの見込み: 23:00 開始（21:30 に確定）
```

## 5. 開催確定フェーズ

### 5.1 開催決定メッセージ
- **送信タイミング**: 締切（21:30）到達時、4名全員が時刻選択済みだった場合に即時投稿
- **メンション**: 参加者（＝ 4名）
- **本文**（例）:
  ```
  🎉 桃鉄1年勝負、開催です！

  開始: 23:00
  回答内訳:
  - メンバーA : 22:30
  - メンバーB : 23:00
  - メンバーC : 22:00
  - メンバーD : 22:30
  ```

### 5.2 15分前リマインド
- **送信タイミング**: 開始時刻の 15 分前
- **メンション**: 参加者（＝ 4名）
- **本文**（例）:
  ```
  ⏰ 15分後に開始です（23:00 開始）
  ```
- **取りこぼし対策**: 開催確定からリマインド予定時刻まで10分未満の場合、**リマインドは送らない**（直前メッセージとなり冗長のため）。

---

## 6. 中止・順延フェーズ

### 6.1 中止メッセージ
- **送信タイミング**: 中止確定の瞬間
- **メンション**: 金曜日の中止で直後に順延確認を出す場合は無し（順延確認側で固定4名全員にメンションする）。土曜日の中止など次アクションが無い最終通知では固定4名全員。
- **本文**（例）:
  - 欠席による中止:
    ```
    🛑 今回は予定がそろわなかったため、お流れです。
    ```
  - 未回答による中止:
    ```
    🛑 21:30 までに4人分の回答がそろわなかったため、今回はお流れです。
    ```

### 6.2 順延確認メッセージ
- **送信タイミング**: **金曜の週次自動募集の中止時のみ**、中止メッセージの直後に別メッセージで送信
  - 手動募集は金曜を含め順延しない。土曜日（順延先）も再順延しない（§6.3）
- **メンション**: 固定4名全員
- **本文**（例）:
  ```
  🔁 今回はお流れです。明日も募集しますか？

  元の候補日: 2026-04-24(金) 22:00 以降
  順延先: 翌日 22:00 以降
  回答締切: 候補日翌日 00:00 JST

  【回答状況】
  - メンバーA : 未回答
  - メンバーB : 未回答
  - メンバーC : 未回答
  - メンバーD : 未回答

  明日も募集OK = 明日もう一度、出欠確認を送ります（参加確定ではありません）
  全員分そろえば明日の出欠確認へ進みます。そろわなければ順延は行いません。
  ```
- **ボタン**: `明日も募集OK` / `順延しない`
- **判定**:
  - 4名全員が `明日も募集OK` を押した → `POSTPONED` 成立直後に、翌日（土曜）回の出欠確認を作成・送信
  - 1人でも `順延しない` を押した → その募集系列は終了
  - 本日 24:00 までに4名全員の回答が揃わなかった → その募集系列は終了

### 6.3 順延の制約
- **週次自動募集の順延は1回のみ**（金曜→土曜の1段階）。土曜日に中止となった場合は順延確認を出さず、その募集系列を終了する。別日の手動募集は可能。
- 順延後（土曜日）の運用は、送信時刻・締切・集計ルールとも金曜日と同じ（締切 土 21:30、22:00 以降開催）。
> 土曜回の送信は金曜 `POSTPONED` 成立直後、締切・集計は本節のとおり。

### 6.4 順延期限の表記
- 「本日 24:00」は **候補日翌日 00:00 JST** を指す慣習表記であり、仕様上サポートするのはこの表記のみ。`25:00` などの 24 超え表記は受け付けない。

## 7. 管理コマンド（スラッシュコマンド）

全て実行権限は固定4名のみ。

| コマンド | 機能 |
|---|---|
| `/ask` | 当日21:30より前に手動募集を起動（§3.1 の日付・進行中制約あり） |
| `/cancel_week` | 今週の未作成の金曜自動募集を停止 |
| `/status` | 当週の自動募集設定と、週をまたいだ進行中の募集を実行者だけに表示 |

### `/cancel_week` の副作用
- 当週の自動募集が未作成の場合だけ、週次予定を停止し、チャンネルに停止通知を1件保存・投稿する。Sessionは作らない。
- 自動募集が生成済みなら、投稿待ち・送信失敗・終了済みであっても変更しない。停止済みの再実行も追加通知を作らない。
- 既存の手動・自動・順延募集、回答、ボタン、リマインド、通知の再送には影響しない。停止後も手動募集を利用できる。
- 実行者だけに見える確認ダイアログで対象の週を固定する。週が変わった確認は副作用なしで拒否する。

---

## 8. データ永続化（論理モデル）

Bot 再起動時の状態復元と重複実行防止のために、以下の論理モデルを永続化する。物理スキーマ・テーブル名・カラム名・整合制約の実装手段は要求仕様の対象外とする。

### 8.1 Session（開催候補日ごとの募集）
開催候補日ごとに最大1件。週次予定とは別に、以下の情報を保持する：

- **週キー**: 開催候補日のISO week表記。分類用であり、募集の識別子ではない
- **開催候補日**（JST）
- **生成元と親**: 手動、週次自動、順延、旧データを区別し、順延先は親の募集に一意に対応する
- **操作識別子**: 手動操作の再送を別募集と区別する
- **順延回数**: 0（手動・週次自動）または1（土曜への順延）
- **状態**: `ASKING` / `POSTPONE_VOTING` / `POSTPONED` / `DECIDED` / `CANCELLED` / `COMPLETED` / `SKIPPED`
  - 終端状態は `COMPLETED`、`POSTPONED`、旧運用の `SKIPPED`。新しい `/cancel_week` はSessionを変更しない
  - `CANCELLED` は中止確定直後の一時状態で、順延判定または募集の終了処理を経て `COMPLETED` または `POSTPONED` に遷移する
  - `POSTPONE_VOTING`: 金曜 `ASKING` 中止後の順延意思確認フェーズ
  - `POSTPONED`: 順延投票で全員 OK が揃ったことを示す終端（成立直後に土曜 `ASKING` を新規作成）
- **中止・完了の理由**（`cancelReason` 例）
  - `absent_cancelled` / `unanswered_cancelled` / `postpone_ng` / `postpone_unanswered` / `saturday_cancelled`
- **運用チャンネル**および、募集メッセージ・順延確認メッセージを指す識別子（再描画のために必要）
- **締切日時** / **リマインド予定時刻** / **リマインド送信済み時刻**
- **確定した開始時刻**（開催確定時のみ）

**一意性**: §3.1 の日付と進行中の制約を守る。旧スキップ用の仮Sessionと証明できる行だけは日付の占有対象外とし、履歴・参照を保持する。旧データの生成元を曜日から自動と推測しない。

**週次予定**: ISO週ごとに自動募集の停止日時・実行者と、生成済みならそのSessionを保存する。日付やSessionの状態とは独立して停止・生成を判定する。

### 8.2 Response（各メンバーの回答）
- Session・メンバー・選択肢（`T2200` / `T2230` / `T2300` / `T2330` / `ABSENT` / `POSTPONE_OK` / `POSTPONE_NG`）・回答時刻。
- 同一 Session × メンバーで一意（最新回答で上書き）。

### 8.3 開催履歴（将来の桃鉄戦績集計システムと統合前提）
永続的に保持：
- **HeldEvent**: 実開催日・開始時刻・紐づく Session・参加メンバー一覧。

### 8.4 保存しないもの
- 回答の変更履歴（最新の回答のみ保持）
- 中止回の詳細（Session には残るが `HeldEvent` は作成しない）

## 9. 状態遷移

```
         ┌──────── /ask, 金08:00 ──────┐
         ▼                              │
     [ASKING] ──── 欠席押下 ───→ [CANCELLED] ──┐
         │                                     │
         │ 締切到達                            │
         ├── 未回答あり ────────→ [CANCELLED] ─┤
         │                                     │
         └── 全員時刻選択 ──→ [DECIDED] ──→ [COMPLETED]
                                   │
                                   ▼ 開始時刻到達の15分前
                               リマインド送信（送信時刻を記録）

   [CANCELLED] ┬─ 金曜の週次自動 ─→ [POSTPONE_VOTING]
               │              │
               │              ├── 全員OK ─→ [POSTPONED] ─→ 翌日 順延回数=1 の新 [ASKING] 生成
               │              ├── 1人NG ─→ [COMPLETED]（理由: 順延 NG）
               │              └── 当日 24:00 未完 ─→ [COMPLETED]（理由: 順延未完）
               │
               └─ 手動・順延先 ─→ [COMPLETED]（順延確認は出さない）

   /cancel_week は未作成の週次自動予定だけを停止（Sessionの遷移なし）
```

### 9.1 DECIDED から COMPLETED への遷移
- `DECIDED` 状態の Session は、15 分前リマインドの送信処理が完了した時点（リマインド不要条件に該当する場合はその判定時点）で `COMPLETED` に遷移する。
- Bot は実開催そのものの監視・終了判定を行わない。

### 9.2 状態遷移の要求
- **同時操作に耐えること**: 4 名が同時に押しても、外部タイマと同時に発火しても、二重処理・状態の取り違え・回答のロストが発生しない。
- **再起動に耐えること**: Bot が再起動しても、進行中の Session は永続化された状態だけから復元でき、締切・リマインド判定が継続される。
- **生成と停止の競合**: 自動募集の生成と週次停止は直列に確定し、生成済みの自動募集を後から取り消さない。延期の親終了と子生成も同時に確定する。
- **表示と状態の分離**: 募集・順延確認メッセージの編集失敗は状態遷移を取り消す理由にならない。メッセージは常に永続化された状態から再構築する。

## 10. 決定済み仕様サマリー

| 項目 | 決定内容 |
|---|---|
| 基準タイムゾーン | JST (`Asia/Tokyo`) 固定 |
| 締切 | 開催候補日当日21:30 JST。手動募集も同じ |
| 自動送信 | 金 08:00 JST（順延時は金曜 `POSTPONED` 成立直後に土曜回を作成・送信） |
| 回答UI | 5ボタン（22:00/22:30/23:00/23:30/欠席）を1メッセージ内に配置 |
| 集計 | 「それ以降参加可能」解釈、開始時刻 = 選択時刻の最遅値 |
| 欠席挙動 | 1人でも欠席→即中止、残り回答打ち切り |
| 回答変更 | 締切まで可、中止確定後は不可 |
| 順延判断 | 4名全員が「明日の募集OK」で翌日再出欠。1人でもNG or 当日 24:00 までに未完なら順延終了 |
| 順延期限表記 | `24:00` は「候補日翌日 00:00 JST」として解釈する唯一の慣習表記 |
| 順延回数 | 1回のみ（土曜まで）。土曜中止時は順延確認なし |
| 週キー | 候補日のISO週。別日の募集を区別し、金曜自動と土曜順延は同じ週に属する |
| メンション | 出欠確認・順延確認 = 4名全員 / 金曜中止通知 = 無し（直後の順延確認でメンション） / 土曜中止など最終通知・開催決定・15分前リマインド = 参加者（4名） |
| 投稿先 | 専用チャンネル1箇所 |
| コマンド権限 | 固定4名のみ |
| 自動募集の停止 | `/cancel_week` は未作成の金曜自動募集だけを停止。手動募集は可能 |
| 履歴保存 | 開催日・開始時刻を永続保存（将来の戦績集計システムと統合前提） |

## 11. OCR・分析の完了通知

- OCR完了（A）は1回の読み取り操作で送った全画像の終了後、送出ごとに1投稿で通知する。追加・再読み取りは別送出。完了日時、既知の文脈、現在の下書きへのリンクと、失敗した画像種別・安全な理由だけを載せる。全失敗も通知し、成功・要確認の一覧・件数、OCR値、生テキスト、画像、例外全文は載せない。長い表示名は省略を明示して短縮する。
- 分析完了（B）は成功した論理ジョブ単位に、前回成功から追加・更新された試合、全4人の順位・銀次回数、銀次合計、メモ全文、作品通算・シーズン通算の前後の平均順位・対象試合数・差分を通知する。作品・シーズン通算は全マップを含む。掲載するシーズンは追加・変更・削除の影響範囲（削除前・移動前後も含む）。通知対象の判定と入力基準は [共有通知契約](../../momo-db/docs/discord-notifications.md#分析通知の入力基準) に従う。手動・保守目的だけの再計算や入力差分のない成功は通知しない。
- 比較不能・初回・対象なし・結果再利用を区別し、丸めるとゼロになる微小差分も変化の有無を伝える。削除だけの変更で掲載試合がない場合も、その旨と影響する集計を表示する。
- 分析結果は成果物 ID で識別し、通知を発生させた論理ジョブ ID と分ける。元ジョブの履歴整理後も比較でき、保存済みの再利用通知は前後に同じ成果物を置く。
- メモ未入力の欄は省略し、追加・変更試合なしと全員銀次 0 回を区別する。
- Aの本文は送出全体の確定時点、Bの本文は成功時点の固定内容。メモ・表示名は公開処理末尾の一括取得時点で固定し、取得後から commit までの編集は取り込みを保証しない。後日の編集では変えず、Bの長文は欠落なく連番へ分割する。リンク先は現在の試合詳細と最新分析であり、通知時点を固定した分析画面ではない。
- Summit の新規受付には本文容量、掲載試合・影響シーズン数、名称・表示名・メモの Unicode コードポイント数、描画後の投稿数の上限を設ける。超過は永続受付前に拒否し、切捨てた分析通知は作らない。値は [notification config](../src/notifications/config.ts)、受付・既受理通知の互換条件は [DB 規約 §6](../docs/db-rule.md#6-ocr分析通知の保存と取消) に従う。momo-result の送出上限より厳しい Summit 側の受付制約であり、producer の分割・再送を追加するものではない。
- A/Bはメンションしない。既存の出欠確認・週取消・リマインドとは独立し、A/BのON/OFFは出欠通知へ影響しない。
- 永続受付前の停止・通信失敗では欠落し得る。受付後は保存した同じ通知を上限付きで再送する。受付成功は配送完了を意味せず、応答喪失・送達不明では重複し得る。
- A/BごとのOFF、確定時（Bは成功時）と現在の設定世代の不一致、Aの下書き確定・取消・削除、Bに掲載した試合の削除は取消条件。Bは全体を取り消す。既送信分は残り、送信開始済みの部分は届く場合がある。
- AのON/OFFは全体確定時に判断し、OFFで確定した送出を後のONで補完しない。再ON・再起動で取消を復活させない。保持中の適格なFAILEDだけ、運用者が同じ通知IDを指定して有限の再試行を開始できる。未受付の通知を業務データから作り直さない。
